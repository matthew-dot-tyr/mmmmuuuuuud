# bolshie-chleni

Backend API тренажёра переговоров: FastAPI + Qwen через OpenRouter + Supabase.

Диалог ведёт AI-модуль (`ai/`, точка входа — `presets.py`), бэкенд отвечает за
игрока: доступ к сложностям, начисление XP и уровни.

## Запуск

```bash
git clone https://github.com/matthew-dot-tyr/arena-negotiations-backend
cd arena-negotiations-backend

python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env            # заполнить ключи
uvicorn main:app --reload
```

Документация и ручные запросы: http://127.0.0.1:8000/docs

Один раз на проект Supabase накатить миграции из `migrations/`
(SQL Editor → New query → вставить файл → Run), по порядку:

| Файл | Что создаёт |
|---|---|
| `001_users.sql` | таблицу `users` и функцию `add_xp` для атомарного начисления |
| `002_negotiations.sql` | таблицу `finished_negotiations` — защита от повторного начисления |
| `003_custom_situations.sql` | лимит генераций в час (`generation_limits` + функция), лог начатых переговоров (`negotiations`), лог отказов (`refusal_log`) |

| `SUPABASE_JWT_SECRET` | да | проверка JWT от Supabase Auth (magic link), см. раздел "Аутентификация" |
| `OPENROUTER_API_KEY` | да | доступ к модели |
| `QWEN_MODEL` | нет | модель, по умолчанию `qwen/qwen3.8-flash-20260826` |

| `SESSION_SECRET` | на деплое | ключ подписи состояния переговоров |
| `CORS_ORIGINS` | нет | домены фронтенда через запятую |
| `XP_PER_LEVEL` | нет | шаг уровня в XP, по умолчанию 100 |
| `LIMIT_CUSTOM_PER_USER` | нет | сколько кастомных сценариев на пользователя в час, по умолчанию 10 |
| `LIMIT_THEME_PER_USER` | нет | то же для тематических сценариев, по умолчанию 30 |
| `LIMIT_PER_IP` | нет | лимит генераций в час на IP, по умолчанию 40 |
| `LIMIT_TURNS_PER_USER` | нет | лимит ходов диалога в час на пользователя, по умолчанию 120 |

Реальный `.env` в гит не коммитим, ключи передаём в личке.

Без `SESSION_SECRET` ключ подписи генерируется случайным на время работы
процесса: после перезапуска сервера незакрытые переговоры придётся начать
заново, а несколько воркеров не поймут подписи друг друга.

## Аутентификация

Все эндпоинты переговоров и игрока требуют вход через **Supabase Auth
(magic link, без пароля)**. `user_id` нигде не принимается от клиента ни в
теле запроса, ни в пути — сервер сам достаёт его из `sub` подписанного JWT.
До этой версии `user_id` был обычным полем в теле запроса, и любой мог
подставить чужой id и читать/портить чужой прогресс — так делать было нельзя.

Каждый запрос к `/user`, `/user/me`, `/negotiation/start`, `/negotiation/turn`
несёт заголовок:

```
Authorization: Bearer <access_token>
```

`access_token` — то, что Supabase Auth выдаёт после входа по magic link
(`supabase.auth.signInWithOtp({ email })` → пользователь переходит по ссылке
из письма → `supabase.auth.getSession()` отдаёт `access_token`). Без
заголовка или с невалидным/просроченным токеном — `401`.

Проверка (`auth.py`) идёт по заголовку `alg` в самом токене — Supabase
подписывает по-разному в зависимости от проекта:
- **HS256** (старые проекты / явно оставленный "Legacy JWT Secret") — общий
  секрет, `SUPABASE_JWT_SECRET`, проверка полностью локальная;
- **ES256/RS256** (новые проекты по умолчанию, JWT Signing Keys) — подпись
  асимметричная, серверу нужен только публичный ключ, который он сам достаёт
  с `{SUPABASE_URL}/auth/v1/.well-known/jwks.json` (эндпоинт публичный, без
  авторизации) и кэширует через `jwt.PyJWKClient`.

Держите `SUPABASE_JWT_SECRET` заполненным в любом случае (нужен для HS256-
ветки и как задел на случай, если в дашборде переключат режим подписи) — на
живом токене выяснилось, что новые проекты Supabase по умолчанию используют
именно ES256, а не HS256, так что реальный трафик в основном пойдёт через
JWKS-ветку.

**Что включить в дашборде Supabase** (Authentication → Providers → Email):
Email-провайдер включён по умолчанию на новых проектах — magic link просто
работает через `signInWithOtp`, пароль вводить не нужно. Проверьте
Authentication → URL Configuration → Redirect URLs — туда должен попасть
адрес страницы, на которую вернётся пользователь после клика по ссылке в
письме (для локальной разработки — адрес `/play`, например `http://127.0.0.1:8000/play`
или откуда фактически открыт фронтенд). `SUPABASE_JWT_SECRET` — Project
Settings → API → JWT Settings → JWT Secret (там же видно, какой режим подписи
у проекта — Legacy или JWT Signing Keys).

`static/play.html` и `play.py` не реализуют сам вход по magic link (это
требует публиковать `SUPABASE_URL`/anon-ключ в браузере — сознательное
решение, не сделано автоматически): обе странички просят вставить уже
готовый `access_token` один раз и дальше используют его в заголовке
`Authorization` (браузер — `localStorage`, консоль — файл `.play_token`,
в `.gitignore`).

## Как идут переговоры

Сценарии и историю диалога мы нигде не храним. Состояние уходит клиенту
в `session_token` (подписанная строка) и возвращается следующим запросом как
есть. Клиенту его читать и менять не нужно — подпись не сойдётся.

```
POST /negotiation/start  ->  сценарий, первая реплика, session_token, options
POST /negotiation/turn   ->  continue: true  — реплика оппонента, новый session_token
                             continue: false — итог, оценка, XP
```

### POST /negotiation/start

Режим по теме (`mode` можно не передавать — по умолчанию `theme`; `user_id` в
теле нет — см. "Аутентификация", он берётся из заголовка `Authorization`):

```json
{ "mode": "theme", "theme": "work", "difficulty": 1 }
```

Темы: `work`, `money`, `purchase`, `personal`. Сложность 1-3, но **не выше
уровня игрока** — иначе 403.

Режим своей ситуации — вместо `theme` присылаем `custom_situation` (30-400
символов, без ссылок):

```json
{ "mode": "custom", "custom_situation": "...", "difficulty": 1 }
```

`theme` и `custom_situation` взаимоисключающие — при рассинхроне с `mode`
запрос отклоняется 422 ещё на уровне схемы.

Успешный ответ (контракт не менялся): `negotiation_id`, `session_token`,
`scenario_text`, `counterpart_opening`, `counterpart_role/tone/goal`, а на
сложностях 1-2 ещё и `options`. **Поля `max_turns` в ответе больше нет** —
официального лимита ходов нет, диалог идёт, пока модель сама не решит его
закончить (см. "Коды отказа" и раздел про `SAFETY_MAX_TURNS` ниже).

Если сценарий построить не вышло (локальная проверка, лимит генераций или
отказ модели — актуально только для `mode=custom`), ответ **200**, не ошибка:

```json
{ "rejected": true, "reason": "too_vague", "message": "Описание слишком общее..." }
```

### POST /negotiation/turn

```json
{ "session_token": "...", "option_id": "a" }
```

На сложности 3 вместо `option_id` — `message` со свободным текстом.

Пока диалог идёт:

```json
{ "continue": true, "counterpart_reply": "...", "session_token": "...", "options": [...] }
```

Когда переговоры закончились:

```json
{
  "continue": false,
  "counterpart_reply": "...",
  "outcome": "success",
  "score": 9,
  "feedback": {
    "broke_quote": null,
    "broke_reason": null,
    "what_worked": "Начали с обоснования цифры, а не с торга",
    "alternative_phrasing": null,
    "tip": "Не называйте уступку первым — дайте оппоненту обозначить его рамку"
  },
  "xp_gained": 45,
  "xp": 45,
  "level": 1,
  "level_up": false
}
```

`feedback` — структурный разбор диалога. Заполнен всегда только `tip`,
остальные четыре поля могут быть `null` (например, при чистом успехе ничего
не "ломалось"). **Если модель дважды не смогла собрать структуру, `feedback`
приходит обычной строкой вместо объекта** — клиент обязан проверять тип
(`typeof feedback === "string"`), см. `static/play.html::renderFeedback`.

Официального лимита ходов в контракте нет — диалог идёт, пока модель сама не
решит его закончить (естественная развязка или явно слабый ход игрока). Есть
только скрытый технический потолок `SAFETY_MAX_TURNS` в `ai/contracts.py`
(защита от зацикливания и неограниченного счёта за API), наружу он не отдаётся.

### Коды отказа (`rejected: true`, HTTP 200)

Отказ — не ошибка сервера: локальная валидация текста, лимит генераций и
отказ модели возвращают одну структуру с машиночитаемым кодом.

| `reason` | Откуда | Когда |
|---|---|---|
| `empty` | локальная проверка | пустой `custom_situation` |
| `too_short` | локальная проверка | короче 30 символов |
| `too_long` | локальная проверка | длиннее 400 символов |
| `contains_link` | локальная проверка | есть ссылка |
| `garbage` | локальная проверка | повторяющиеся символы, мало букв/слов |
| `rate_limited` | лимит | превышен лимит генераций в час (пользователь или IP) |
| `not_a_negotiation` | модель | текст вообще не про переговоры |
| `too_vague` | модель | тема названа, но не с кем/не о чём договариваться |
| `unsafe` | модель | ситуация про насилие, самоповреждение, незаконные действия |

## Эндпоинты игрока

| Метод | Путь | Что делает |
|---|---|---|
| `POST` | `/user` | создаёт профиль текущего (из токена) игрока, если его ещё нет |
| `GET` | `/user/me` | xp, уровень, сколько до следующего, открытые сложности — тоже текущего игрока |
| `GET` | `/scenarios` | CRUD старого SQLite-слоя (наследие, под удаление) |

Раньше был `GET /user/{id}` с произвольным id в пути — убран вместе с
остальными местами, где id брался не из токена (см. "Аутентификация").

## Коды ошибок

| Код | Когда |
|---|---|
| 400 | плохой `option_id`, испорченный `session_token`, ошибка контракта движка |
| 401 | нет заголовка `Authorization`, токен невалиден/просрочен |
| 403 | сложность закрыта либо токен принадлежит другому игроку |
| 409 | эти переговоры уже засчитаны |
| 422 | невалидное тело запроса |
| 500 | `SUPABASE_JWT_SECRET`/`SUPABASE_URL` не заданы на сервере (ошибка конфигурации, не запроса) |
| 503 | модель не ответила или вернула мусор после повторов |

## Начисление XP

- провал: фиксированно 5 XP
- успех: `score × множитель сложности`, множители `{1: 5, 2: 8, 3: 12}` — см. `progress.py`
- уровень из суммарного XP: 100 XP — 2 уровень, 200 XP — 3 (максимум)

В `ai/xp.py` лежит более старая формула (`score × difficulty × 2`). Она
сознательно **не экспортируется** ни из `presets.py`, ни из `ai/__init__.py`
(было дублирование двух формул — риск, что кто-то вызовет не ту). Файл
остался только для ручного `test_offline.py`, который импортирует его напрямую
для проверки движка в изоляции. Единственный источник правды для XP в
продакшен-коде — `progress.py::calculate_xp_gain`.

## Решения по мержу кастомных ситуаций (21.09)

Зафиксировано задним числом, как просила инструкция промпт-инженера —
формально это нарушение заморозки контракта выхода, но структурный разбор
сильнее плоского текста, откатывать не стали.

| № | Вопрос | Решение |
|---|---|---|
| 1 | Структурный разбор `feedback` (объект из 5 полей вместо строки) | **Принято.** `/negotiation/turn` при `continue: false` отдаёт `feedback` как объект (или строку — деградация, см. выше). Единственное изменение контракта `/negotiation/start` не коснулось. |
| 2 | `SAFETY_MAX_TURNS = 20` — без игрового лимита ходов стоимость непредсказуема | **Оставлено 20, лимит ходов в час добавлен (`allow_turn`/`LIMIT_TURNS_PER_USER`), но пока не подключён к эндпоинту.** Снижать технический потолок или считать ходы вместо стартов — нужны цифры (средняя/максимальная длина диалога по сложностям), они не измерялись вживую в этом заходе, чтобы не тратить бюджет OpenRouter без явного запроса. `rate_limit.allow_turn()` готов, но `main.py` его не вызывает — подключить после того, как будут собраны реальные данные о длине диалогов. |
| 3 | Сложность 3: «манипулятивный» → «действует строго по принципам» | **Принято как есть из архива.** Не перепроверялось живыми прогонами `check_quality.py` на различимость сложностей 1 vs 3 — рекомендуется сделать перед приёмкой. |
| 4 | Максимальная длина `custom_situation`: 400 или 1000 | **400** — как в задании. `ai/contracts.py::CUSTOM_SITUATION_MAX_LEN` и `validation.py::MAX_LEN` синхронизированы. |

Также применено решение бэкендера 1 (шаг 8, не из четырёх пунктов выше, но
из того же документа): `calculate_xp` убран из экспортов `presets.py` и
`ai/__init__.py` — единственный источник правды по XP теперь `progress.py`.

## Аутентификация (добавлено позже)

`user_id` был обычным полем в теле `/negotiation/start`, `/negotiation/turn`
и `/user`, и путём в `/user/{id}` — то есть любой клиент мог подставить чужой
id и прочитать или испортить чужой прогресс, проверки не было вообще. Заменено
на Supabase Auth (magic link, без пароля): `user_id` теперь только `sub` из
подписанного JWT в заголовке `Authorization: Bearer`, см. раздел
"Аутентификация" выше и `auth.py`. `GET /user/{id}` стал `GET /user/me`.
