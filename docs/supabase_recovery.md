# Восстановление Supabase после закрытия старого проекта

Старый проект Supabase (`ovsdpfcygsfugspjtiit.supabase.co`) закрыт — этим
объясняется `SSL: UNEXPECTED_EOF_WHILE_READING`, который вылезал при любом
обращении к базе. У вас остался дамп `db_cluster-26-09-2026@14-36-25.backup.gz`
(скачан из Database → Backups старого проекта) — это полный `pg_dumpall`,
269 КБ несжатым, 7500 строк SQL.

## Что реально внутри бэкапа

Дамп — это **весь кластер**, а не только ваши данные:

| Раздел дампа | Что это | Нужно ли восстанавливать |
|---|---|---|
| `CREATE ROLE ...` (anon, authenticated, supabase_admin, ...) | служебные роли платформы Supabase | **Нет** — новый проект создаёт их сам при провижининге |
| Схемы `auth`, `storage`, `realtime`, `graphql`, `vault`, `pgbouncer` | внутренние схемы платформы (Auth, Storage, Realtime) | **Нет** — управляются Supabase, версия схемы привязана к текущей версии платформы; в `vault.secrets` вдобавок ключи шифрования старого проекта, в новом они не расшифруются |
| `auth.users`, `storage.buckets` | реальные данные Auth/Storage | Пусто — приложение их не использует (свои `user_id` без Supabase Auth) |
| Схема `public`: `users`, `finished_negotiations`, функция `add_xp` | **ваши** таблицы | **Да** — это единственное, что реально нужно |
| Данные `public.users` / `public.finished_negotiations` | 5 тестовых игроков, 7 завершённых переговоров | По желанию — это данные с разработки, не прод |

Заметьте: в дампе нет `public.negotiations`, `public.refusal_log`,
`public.generation_limits` — бэкап снят 26.09, до того как мы накатили
миграцию `003_custom_situations.sql` на старом проекте. Это не потеря:
файл миграции лежит в репозитории и создаёт их заново.

## Почему НЕ восстанавливать дамп целиком

Соблазн — накатить весь `full_dump.sql` через `psql` на новый проект, чтобы
получить точную копию. **Не делайте так**:

1. Роли (`CREATE ROLE anon`, `supabase_admin` и т.д.) уже существуют в новом
   проекте и управляются платформой — конфликт имён, восстановление упадёт
   на первой же строке ролей (или, если проигнорировать ошибки флагом
   `--continue`, тихо перезапишет то, чем управляет платформа).
2. Схемы `auth`/`storage`/`realtime` в новом проекте могут быть **другой
   версии** (Supabase их обновляет), чем те, что зафиксированы в дампе —
   восстановление старой версии поверх новой ломает Auth/Storage.
3. `vault.secrets` зашифрован ключом, который принадлежал старому,
   закрытому проекту. В новом проекте этот ключ недоступен физически —
   восстановленные секреты будут нечитаемым мусором.
4. Ничего из auth/storage/realtime всё равно не используется этим
   приложением (см. таблицу выше — обе служебные таблицы с данными пустые).

Единственное, что вам действительно принадлежит и нужно — таблицы в схеме
`public`. Они уже полностью описаны в `migrations/001_users.sql`,
`migrations/002_negotiations.sql`, `migrations/003_custom_situations.sql`.
Проще и безопаснее накатить их заново, чем распутывать конфликты дампа.

## Шаг 1. Создать новый проект Supabase

1. https://supabase.com/dashboard → **New project**.
2. Организация, имя проекта, пароль базы (сохраните его отдельно — он не
   в этом гайде и не в дампе), регион — тот же, что был у старого, для
   минимальной задержки. Тарифный план — тот же, что использовали раньше.
3. Подождите пару минут, пока проект провиженится.

## Шаг 2. Забрать ключи и обновить `.env`

В новом проекте: **Project Settings → API**.

| Взять отсюда | Положить в `.env` |
|---|---|
| Project URL | `SUPABASE_URL` |
| `anon` `public` ключ (или `service_role`, если нужен полный доступ мимо RLS — в этом проекте RLS не используется, `anon` может не пройти, если в новом проекте default RLS включён; при ошибках доступа переключитесь на `service_role`) | `SUPABASE_KEY` |

Файл `.env` в этом репозитории (не в архиве и не в гите):

```bash
SUPABASE_URL=https://<новый-project-ref>.supabase.co
SUPABASE_KEY=<новый ключ>
```

Остальные переменные (`OPENROUTER_API_KEY`, `SESSION_SECRET` и т.д.) не
трогаем — они не связаны с базой.

> Напоминание из прошлого разбора: ключ **OpenRouter** тоже стоит
> перевыпустить, он не имеет отношения к закрытию Supabase-проекта, но всё
> ещё висит как открытый пункт с прошлого раза.

## Шаг 3. Накатить схему — три миграции по порядку

В новом проекте: **SQL Editor → New query**. Выполнить **по одному файлу за
раз, в этом порядке** (второй и третий зависят от таблиц из первого):

1. `migrations/001_users.sql` — таблица `users`, функция `add_xp`
2. `migrations/002_negotiations.sql` — таблица `finished_negotiations`
3. `migrations/003_custom_situations.sql` — `generation_limits`,
   `negotiations`, `refusal_log`, функция `check_and_increment_generations`

Все `CREATE TABLE IF NOT EXISTS` — идемпотентны, случайный повторный запуск
ничего не сломает.

## Шаг 4. (Опционально) вернуть тестовые данные из бэкапа

Если хочется сохранить 5 тестовых игроков и историю их переговоров с
разработки — выполните в SQL Editor:

```
migrations/restore_backup_data_2026-09-26.sql
```

Это обычные `INSERT ... ON CONFLICT DO NOTHING` с данными, которые я достал
из `COPY public.users` / `COPY public.finished_negotiations` в дампе (сырой
`COPY ... FROM stdin` — протокол клиента `psql`, веб-редактор SQL его не
понимает, поэтому конвертировал в `INSERT`). Если новый проект должен
начинаться с чистого листа — просто не выполняйте этот файл.

## Шаг 5. Проверить

```bash
python -m scripts.check_users
python -m scripts.check_progress
```

Или через API (сервер должен быть поднят с новым `.env`):

```bash
uvicorn main:app --reload
```

```bash
curl -X POST http://127.0.0.1:8000/user -H "Content-Type: application/json" -d "{}"
curl http://127.0.0.1:8000/user/<user_id-из-ответа-выше>
```

200 и корректный JSON — база подключена и работает. Дальше можно гонять
`pytest -q` (он всё равно ходит через заглушки, не через реальную базу) и
живой прогон `python play.py`.

## После восстановления

- Файл `db_cluster-26-09-2026@14-36-25.backup.gz` (и его распакованная копия,
  если она у вас где-то лежит) можно удалить или убрать в приватное хранилище
  — паролей внутри нет, но это полная структура вашей БД, лишняя копия
  на диске ей не нужна.
- Убедитесь, что `.env` с новыми ключами не попал в git (`.gitignore` уже
  его исключает — но `git status` перед первым коммитом после этого лишним
  не будет).
